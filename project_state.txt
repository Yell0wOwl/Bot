СОСТОЯНИЕ ПРОЕКТА: AI-бот для детейлинг-студий (Telegram + база знаний из прайс-листа)
Актуально на 29.09.2026, вечер (универсальный формат базы, запись с подтверждением кодом, три прогона тестов на Gemini). Файл для передачи контекста в новый чат с Claude: вставьте его целиком и напишите задачу.

====================================================================
1. КОНТЕКСТ
====================================================================
Команда из трёх человек продаёт детейлинг-студиям Москвы ИИ-агента, который отвечает клиентам
в мессенджере по прайсу студии. План запуска — 8 недель (с 22.09.2026), см. PDF
«План_запуска_детейлинг,_Москва_—_8_недель.pdf» в папке проекта.
  • Фархад — продажи, переговоры, список студий.
  • Григорий (владелец этого кода) — скелет агента, парсер прайса, сборка ботов под клиентов.
  • Илья — аудит скорости ответа студий, персонализация прототипов, чтение диалогов.
Ключевые требования из плана:
  • бот собирается по ссылке на сайт студии «за 15 минут без ручной работы» (нужен ПАРСЕР — пока не написан);
  • прайс детейлинга — матрица «услуга × класс кузова», бот не должен выдумывать цены;
  • тест у клиента: 5 дней на реальном трафике, каждый диалог виден, смотрим «сколько обращений обработал
    и сколько записал»; метрики для кейса: время первого ответа, доля отвеченных, записи без человека,
    обращения вне рабочих часов.

Пользователь пишет по-русски, работает на Windows, Python 3.13, PyCharm, виртуальное окружение .venv
в папке проекта: C:\Users\s0va_\Desktop\AI_BOT (есть git-репозиторий).
Предпочтения пользователя: минимум лишнего кода и опций; скрипты запускаются без аргументов командной
строки; настройки — в .cfg (INI) файлах; при смене модели меняется только файл инференса; объяснять
«почему», а не только «что»; перед крупной правкой уточнять.

====================================================================
2. ЧТО УМЕЕТ БОТ СЕЙЧАС
====================================================================
  • Отвечает на вопросы о ценах, услугах, адресе, графике работы, гарантии — по JSON-базе знаний студии.
  • Цены берёт только через инструменты (tool calling); строки цен форматирует код, модель их пересказывает.
  • Работает в консоли (run.py) и в Telegram (telegram.py), прогоняется на 100 тестовых диалогах (test.py).
  • Модель: облачная Gemini Flash (локальная модель из проекта удалена 29.09).
  • Пишет лог всех вопросов, вызовов инструментов, ответов и времени в log.txt.
  • Записывает клиента: собирает имя, телефон, желаемые день и время и услугу; код проверяет, что эти данные
    клиент действительно назвал, вычисляет дату («в четверг» → 1 октября) и показывает заявку на подтверждение
    (в Telegram — кнопками «Да, всё верно» / «Нет, исправить»); подтверждённая заявка пишется в bookings.json
    и отправляется администратору в Telegram-чат (admin_chat_id в telegram.cfg).
НЕ умеет: проверять свободное время и часы работы в заявке (только выходной день), догоняющие сообщения,
Avito, панель/метрики, передачу диалога живому человеку. Парсера сайтов нет — JSON-базы сделаны вручную
(Claude-ом по страницам сайтов).

====================================================================
4. ФОРМАТ БАЗЫ ЗНАНИЙ (JSON) — согласован с пользователем, менять только по его решению
====================================================================
Формат универсальный для разных автосервисов: цена зависит от объявленных компанией ПАРАМЕТРОВ
(класс кузова, тип плёнки, радиус дисков…) или не зависит ни от чего.
{
  "name": "Детейлинг-центр MODNOE MESTO",
  "source_url": "https://modnoe-mesto.com/prays-list/",
  "contacts": {"address": "...", "phone": ["+74958375035"], "email": ["..."],
               "schedule": {"mon": ["10:00", "21:00"], ..., "sun": null}},    // null = выходной
  "parameters": [
    {"id": "body_class", "name": "Класс кузова", "question": "Какой у вас автомобиль?", "type": "choice",
     "ordered": true, "values": [{"code": "1", "name": "1 класс", "examples": ["Kia Rio"]}, ...]},
    {"id": "film_finish", "name": "Тип плёнки", "question": "...", "type": "choice", "default": "gloss",
     "values": [{"code": "gloss", "name": "глянцевая"}, {"code": "matte", ...}, {"code": "color", ...}]},
    {"id": "wheel_radius", "name": "Радиус дисков", "question": "...", "type": "number", "unit": "дюймов"}
  ],
  "service_tree": {"service_classes": [...], "services": [...]},
  "faq": ["Детейлинг-студия: ...", "В стоимость услуг включена официальная гарантия..."],
  "warnings": [{"level": "error|warning|info", "service_class_id": "6.1.23"|null, "service_class": "имя"|null,
                "message": "..."}]
}
Категория: {"id": "6", "name": "Оклейка антигравийной полиуретановой плёнкой",
            "service_classes": [...], "services": [...]}          // оба списка всегда есть, даже пустые
Услуга (лист): {"id": "6.1.15", "name": "Оклейка.../Spectroll Premium/Капот", "unit": null|"за 4 шт.",
                "currency": "RUB", "duration": null, "prices": [ правила цены ]}
Правило цены — условие when и ровно один вид:
  базовая цена       {"when": {"body_class": "3"}, "from": 48000, "to": 48000}   (to = null → «от»)
  надбавка           {"when": {"film_finish": "matte"}, "add_percent": 10}  или  {"when": {...}, "add": 5000}
  к администратору   {"when": {"body_class": "1"}, "ask_admin": true}      — цену бот не называет
when: {} — всегда; "3" — одно значение; ["1","2"] — несколько; {"min": 18, "max": 21} — диапазон числа.
Правила:
  • Дерево — то, что клиент покупает; параметры — свойства машины клиента, меняющие цену одной и той же услуги.
  • name — полный путь через «/»; «/» внутри названий с сайта заменяется словами. id иерархические.
  • default параметра — значение, если клиент ничего не сказал (плёнка по умолчанию глянцевая и т.п.).
  • Надбавки — обычные правила цены при значении параметра (бывшее поле modifiers упразднено);
    несколько надбавок применяются последовательно (×1,1 × 1,15).
  • Опечатки сайта и «цена по запросу» записываются как ask_admin (точечно, на нужные значения параметров).
  • Поле business упразднено: чем занимается компания — первая строка faq.
  • examples у значений параметра — сюда кладётся таблица «модель авто → класс» от студии.
  • schema.py запрещает лишние поля (extra="forbid").
check(): уникальность id, связность дерева, корректность parameters (коды, default), when ссылается только на
объявленные параметры и значения, from ≤ to, есть хотя бы базовая цена или ask_admin, для ordered-параметра
цена не падает и не скачет > 3× между соседними значениями.
В modnoe_mesto.json опечатки сайта стоят как ask_admin: спойлер Spectroll 1 кл. (6.1.23), зона риска «Премиум»
Prime Shield 3 кл. (6.3.4), крышка багажника Prime Shield 5 кл. (6.3.19), полная оклейка винилом 4 кл. (7.1).

====================================================================
5. КАК УСТРОЕН АГЕНТ И ЗАЩИТА ОТ ВЫДУМАННЫХ ЦЕН
====================================================================
Принцип: модель не знает цен. Цены хранит и форматирует код, модель выбирает, что посмотреть, и пересказывает.
  • Системный промпт (agent.py, SYSTEM_PROMPT): роль «администратор компании «{name}»», 10 правил:
      1) факты только из данных; не объяснять от себя, что входит в работы («после осмотра»), не придумывать
         описаний компании и вариантов («автотехцентр», «партнёры»);
      2) цены только через get_prices, дословно из price; 3) параметры — только названные клиентом;
      4) depends_on → диапазон и вопрос;
      5) «УТОЧНИТЬ У АДМИНИСТРАТОРА» / admin_for → цену не называть; к администратору с телефоном — ТОЛЬКО если
         клиент спросил о цене; если не спрашивал — не упоминать ни цену, ни администратора, даже после get_prices
         (иначе из-за принудительного get_prices бот вставлял «стоимость подскажет администратор» в каждый ответ);
      6) чего нет в данных (скидки, акции, время, материалы, сроки, гарантии) — к администратору; про услугу не из
         каталога не говорить «у нас нет», а «в каталоге нет, возможность уточнит администратор»;
      7) срок — только из duration; 8) время работы — по разделу «Сегодня», праздники — к администратору;
      9) запись — собрать имя/телефон/день и время/услугу, не придумывать данные за клиента, время передавать
         словами клиента и дату не вычислять, вызвать create_booking; подтверждает система, время не обещать;
      10) не по теме — вернуть к услугам.
    Стиль: по-русски, на «вы», 1–4 предложения; отвечать только на заданный вопрос (цена, хранение, магазин —
    только если спросили); предлагать запись, только если клиент интересуется конкретной услугой. Блоки: «О КОМПАНИИ», «ПАРАМЕТРЫ ЦЕНЫ» (коды, значения, примеры,
    default), «СЕГОДНЯ» (календарь, пересчитывается при каждом вопросе), «КАТАЛОГ» (id+названия БЕЗ цен).
  • Инструменты (kb.py):
      get_prices(id, params?) — услуга или все услуги категории; params — объект с кодами параметров
        (в схеме инструмента enum по values). По каждой услуге код возвращает: price — готовая строка с учётом
        известных параметров и надбавок («52 800 ₽», «от 28 000 ₽ до 40 000 ₽», «от 69 000 ₽ за 4 шт.» или
        «УТОЧНИТЬ У АДМИНИСТРАТОРА»); depends_on — чего не хватает (параметр + вопрос клиенту); admin_for — при
        каких значениях цену даёт администратор; surcharges — надбавки по несказанным параметрам текстом;
        assumed — какие значения по умолчанию приняты. Непонятные параметры → params_ignored. > 60 услуг —
        список подкатегорий. Подбор: при всех известных параметрах берётся самое конкретное правило.
      search_services(query) — поиск услуг по первым 4 буквам слов.
      create_booking(name, phone, desired_time, service_id | service, comment?) — обрабатывается в agent.py:
        bookings.validate(args, studio, source, client_text), где client_text — все сообщения клиента. Проверки:
          – имя: есть, с буквами, ≤ 60 символов, первые 3 буквы встречаются в словах клиента (ловит «Клиент»);
          – телефон: → +7XXXXXXXXXX (8…/7…/9… из 10–11 цифр) или +<код> из 10–15 цифр, последние 10 цифр есть
            в сообщениях клиента;
          – desired_time: все числа (кроме 0) и слова дня («завтра», дни недели, месяцы) есть в словах клиента —
            модель не может подставить «завтра в 12:00», которого клиент не говорил; день должен определяться
            (resolve_date) — «на следующей неделе» без дня не принимается; выходной по графику отклоняется;
          – услуга: service_id из каталога (несколько — через запятую) или service словами клиента;
          – comment, совпадающий с названием услуги, отбрасывается.
        Ошибка → модели («missing»/«invalid» с подсказкой, что спросить), модель дорасспрашивает клиента.
        Данные в порядке → Agent.pending = заявка, клиенту уходит ТЕКСТ ИЗ ШАБЛОНА (не LLM), цикл прерывается.
  • Подтверждение (Agent.ask при pending / Agent.confirm): короткое «да» → bookings.save() и фиксированный ответ;
    короткое «нет» → «Хорошо, что нужно исправить?»; «передумал», «отмена», «запись не нужна» → заявка отменяется
    (CANCEL_TEXT). Любое другое сообщение уходит модели, а pending сохраняется: исправление («нет, телефон другой: …»)
    → модель вызывает create_booking с новыми данными и показывается новая заявка; вопрос («где вы находитесь?») →
    модель отвечает, а код дописывает к ответу ту же заявку. Повторный create_booking с теми же данными заявку
    второй раз не показывает (модель получает ALREADY_SHOWN и отвечает своим текстом, под которым код снова показывает заявку). Если при
    ожидающей заявке модель пишет «заявка оформлена / принята / подтверждена» (BOOKING_CLAIM_RE), код убирает этот
    текст — оформляет заявку только код после «да». Если клиент пишет «запись не нужна», вызов create_booking
    отклоняется (NOT_WANTED) — даже без ожидающей заявки. В подтверждении ко времени дописывается вычисленная дата
    («в четверг в 14:00 (четверг, 1 октября)»), к услуге не из каталога — пометка «нет в каталоге — возможность
    уточнит администратор». В Telegram кнопки несут
    id заявки (callback_data booking:yes:<id>), старая кнопка новую заявку не подтвердит.
  • Уведомление администратора: сохранённая заявка кладётся в Agent.new_bookings; telegram.py после ответа
    забирает их и шлёт bookings.admin_text() в admin_chat_id (с @username клиента или его id). Ошибка отправки
    пишется в лог и клиенту не мешает. Команда /id в любом чате отвечает id этого чата.
  • Цикл (Agent.ask): до MAX_STEPS=6 вызовов модели; результаты инструментов идут в историю как role=tool;
    история обрезается до 30 сообщений (не с середины вызова).
  • Принудительный вызов инструмента на первом шаге (force_tool_call_first в cloud_inference.cfg):
    в Gemini — tool_choice="any". Введён после того, как ранее опробованная локальная модель отвечала
    «из головы», не вызывая инструменты. Побочный эффект: на любой вопрос модель сначала что-то вызывает
    (обычно get_prices или search_services, иногда create_booking с данными из истории) — отсюда правило 5,
    ALREADY_SHOWN и NOT_WANTED.
  • Проверка чисел: все числа ≥ 100 в ответе должны встречаться в промпте, результатах инструментов или словах
    клиента (телефоны сверяются по подстроке). Иначе — одна повторная попытка с системным замечанием, затем
    ответ «Не могу точно назвать стоимость. Её подскажет администратор по телефону …».
  • Календарь (kb.calendar): «Сейчас четверг, 24 сентября 2026 года, 22:30. Студия сейчас закрыта. Откроется
    завтра, в пятницу 25 сентября, в 10:00.» + график на 7 дней. Время — локальное время компьютера
    (часовые пояса пользователь попросил убрать).

КОНТРАКТ С МОДЕЛЬЮ (agent.py): chat(messages: list[dict], tools: list[dict]) -> Reply
  messages: {"role":"system","content"}, {"role":"user","content"},
            {"role":"assistant","content","tool_calls":[{"id","name","arguments":dict}]},
            {"role":"tool","tool_call_id","name","content": JSON-строка}
  tools: [{"type":"function","function":{"name","description","parameters"}}]
  Reply(content: str, tool_calls: list[ToolCall(id, name, arguments: dict)])
  Посреди истории может быть system-сообщение (замечание проверки чисел) — реализация обязана его принять.

6. МОДЕЛЬ: GEMINI
====================================================================
cloud_inference.py (Gemini, SDK google-genai 2.25, client.interactions.create):
  • store=False — историю ведёт агент; system_instruction — первое system-сообщение; tools переводятся в
    {"type":"function", name, description, parameters}; история → шаги user_input / model_output /
    function_call / function_result; system посреди диалога → user_input «[Системное замечание] …».
  • Gemini требует возвращать шаги «thought» (с подписью) ровно такими, как пришли. В истории агента их нет,
    поэтому модуль кэширует сырые шаги модели по id вызова инструмента или по тексту ответа (_model_steps,
    до 2000 ходов) и подставляет их при сборке следующего запроса.
  • Повтор при 429/5xx: паузы 2, 5, 10 с. Температуры в Interactions API нет.
  • Реальные прогоны делает пользователь у себя (из облачной среды Claude API Gemini недоступен — прокси 403).
    Время ответа в тестах — в среднем 3,0 с, медиана 2,9 с, максимум ~12–30 с (повторы при 429/5xx).
  • Google открывает Gemini API не во всех странах — доступность в регионе запуска бота проверять.
История: раньше пробовали локальную Qwen2.5-7B-Instruct (4 бита, RTX 4070) — без принуждения она не
  вызывала инструменты и выдумывала цены; от локального варианта отказались, код и веса удалены.

7. TELEGRAM (telegram.py)
====================================================================
aiogram 3.x, long polling. Свой Agent на каждый chat_id (name="tg<chat_id>" в логе), /start сбрасывает диалог.
Запросы к модели — по очереди (asyncio.Lock), генерация в отдельном потоке (asyncio.to_thread),
индикатор «печатает…» каждые 4 с, ответы > 4096 символов режутся. Не-текст → not_text_message.
allowed_users: если задан — посторонним отвечает not_allowed_message с их id. История диалогов — только в
памяти (после перезапуска пропадает). Сообщения, пришедшие пока бот был выключен, обрабатываются при старте.
Внимание: файл называется telegram.py — конфликтует с пакетом python-telegram-bot, если его поставить.
